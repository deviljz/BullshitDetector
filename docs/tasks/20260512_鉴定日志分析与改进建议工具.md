## 1. Objective（目标）

**做什么**：
新增 Claude Code skill `/analyze-logs` + 数据准备脚本 `scripts/prepare_log_data.py`，让用户在当前 Claude 会话中调用 skill 后，主 Claude 扫近 N 天的 `logs/*.json` + `history.json`，识别 plan_execute 路径的系统性问题，输出 markdown 报告到 `reports/log_analysis_<YYYYMMDD-HHMM>.md`。

**自迭代能力**：每次分析报告必须包含"工具自身改进建议"section，Claude 反思本次分析过程中遇到的工具缺陷（脚本字段缺失、SKILL 指令模糊、报告结构不够清晰等），列出具体改进项。用户看完报告后可手动指示 Claude 实施这些改进（不允许 Claude 自动改）。

**为什么做**：
- 当前调优靠"用户发现某次跑结果有问题 → 写 spec 修"，被动模式
- 单 case 的偶发问题不易看出规律（LLM 行为漂移、某域名 fetch 失败率上升、phase 2 改善率下降、planner 拆解模式变化等"软模式"）
- 用 grep / Python 统计找已知指标可以，但找**未知模式**（"我隐约觉得有问题但说不清"）需要推理能力
- 复用当前 Claude 会话做分析，零额外 LLM API 调用，零额外开销

**用户是谁**：项目维护者。手动在 Claude Code 中调用 `/analyze-logs`。

**成功标准**（可验证）：
1. `python scripts/prepare_log_data.py --last 7` 在 5 秒内输出结构化 markdown 到 stdout，含至少 6 大字段类（每 case：stages 耗时/tokens、verdict、search query 列表、note、claim 数、outlier 标记）。
2. 用户输入 `/analyze-logs` 后，Claude 按 SKILL.md 指令执行：跑脚本 → 读输出 → 写报告到 `reports/log_analysis_<YYYYMMDD-HHMM>.md`。
3. 报告含至少 5 大 section：基本统计、Top N 问题诊断、建议修法、**工具自身改进建议**、附录（outlier case 链接）。
4. 整个流程**零外部 LLM API 调用**（不调 Gemini/openai 等）。
5. 3 个 unit test 覆盖 `prepare_log_data.py` 的数据加载与字段提取。
6. "工具自身改进建议" section 不为空——每次分析都至少提一条（哪怕是"当前数据足够，无明显工具缺陷"也算 1 条）。

**非目标**：
- 不调外部 LLM API（连 Gemini 都不调）
- 不实现 cron / 定时触发（手动 /analyze-logs 调用足够）
- 不修改 history.json / logs/ 结构
- 不主动改源码或出 patch
- 不发送报告到外部
- 不解析 `logs/bullshit.log`（Python logging 输出，非结构化）

## 2. Commands（提供哪些命令/接口）

### Skill：`/analyze-logs [--last N | --since DATE]`
- 用户在 Claude Code 中输入，触发 SKILL.md 指令
- 参数透传给数据准备脚本

### 脚本：`python scripts/prepare_log_data.py [--last N | --since DATE]`
- `--last N`：分析最近 N 天的 logs（默认 7）
- `--since DATE`：从 ISO 日期起（与 --last 互斥）
- 输出：结构化 markdown 到 stdout，**不写文件**（由 Claude 后续 Write 工具写报告）

## 3. Structure（目录/模块）

```
.claude/skills/analyze-logs/SKILL.md
    ← Skill 定义。指令包含：
        1. 运行 `python scripts/prepare_log_data.py --last <N>` 拿结构化数据
        2. 仔细阅读输出，找系统性问题（不是单 case 偶发）
        3. 用 Write 工具写 markdown 报告到 reports/log_analysis_<YYYYMMDD-HHMM>.md
        4. 报告结构：基本统计 → Top N 问题（每条带 case_id 证据）→ 建议修法 → 工具自身改进建议 → 附录
        5. "工具自身改进建议" section 要求 Claude 反思：本次分析需要但脚本未提供的字段、SKILL 指令模糊导致走弯路的地方、报告结构可优化点。每条改进建议给出具体修法位置（文件名 + 函数名/章节名）。
        6. 输出报告后，主动告知用户："工具改进建议见报告末尾，需要我现在实施吗？"——等待用户明确指示再改脚本/SKILL。
scripts/prepare_log_data.py
    ← 数据准备：加载 logs/*.json + history.json，过滤时间窗，
       按 case 组织关键字段（stages、tokens、verdict、search queries、url_snippets URL 列表、
       note、claim 数、phase2 触发与否、fetch 失败率、outlier 标记），
       输出结构化 markdown 到 stdout
src/analysis/__init__.py
src/analysis/log_loader.py
    ← 纯 Python：load_logs_since(date) + load_history() + per_case_summary(log_entry, history_entry)
src/analysis/markdown_render.py
    ← 把 per_case_summary 列表渲染成 markdown（脚本主体调用）
tests/test_log_loader.py
    ← 数据加载与字段提取单测（构造假 log/history）
reports/
    ← 报告输出（gitignored）
.gitignore
    ← 加 reports/
```

## 4. Style（代码风格 / 依赖选型）

- 脚本只做"准备数据"，**不做分析**——分析交给 Claude
- log_loader / markdown_render 是纯函数，不依赖 src/ai/，可独立测试
- 不引入新依赖（argparse、json、collections、datetime 都是 stdlib）
- 数据准备脚本输出的 markdown 是给 Claude 看的，不是给人看的；结构清晰、字段标注明确，方便 Claude 提取信号
- SKILL.md 不长，但必须包含"找未知模式而非已知告警"的引导
- 报告写到 `reports/` 而非 `docs/`：报告是临时产物、可重生成，不进 git
- Claude 写报告时遵循"具体证据+具体建议"原则：每条 Top N 问题必须引用 case_id 作为证据，每条建议必须可执行（不只是"考虑优化 X"）

## 5. Testing（测试策略）

- **数据加载单测 `tests/test_log_loader.py`**：
  - 构造 fake `logs/*.json`（5 个不同 case，含 1 token 异常、1 fetch 全失败、1 phase2 改善、2 正常）和 fake `history.json`
  - 测试 `load_logs_since("2026-05-10")` 时间窗过滤正确
  - 测试 `per_case_summary(log, history)` 各字段提取正确：stages 数量、tokens、verdict、search query 列表、claim 数、phase2 触发标记
- **报告渲染单测 `tests/test_log_loader.py`** 同文件：
  - mock 几个 per_case_summary → 渲染 → 检查输出 markdown 含预期字段标题、case_id 段
- **集成（人工跑一次）**：
  - 在 Claude Code 输入 `/analyze-logs --last 30`
  - 验证：Claude 跑了脚本、读了输出、写了报告
  - 检查 `reports/` 下报告是否含 4 大 section、是否引用了具体 case_id

## 6. Boundaries（边界）

### 绝不做
- 不调任何外部 LLM API（Gemini、Claude API 等都不调）
- 不解析 `logs/bullshit.log`（只解析结构化 `logs/*.json`）
- 不改 src/ai/ 任何模块（只读访问）
- 不发送报告到外部（邮件 / Slack / API）
- 不自动应用建议或改源码（只产报告）
- 不在 Claude 分析时塞完整 log 原文（脚本已聚合为 per_case_summary，避免 token 浪费）
- 不实现 cron / 定时
- 不在 unit test 中 import `src/ai/` 任何东西
- **不自动改 `scripts/prepare_log_data.py` 或 `.claude/skills/analyze-logs/SKILL.md`**：报告里的"工具自身改进建议"是给用户看的，Claude 必须等用户明确指示"实施这些改进"后才能改

### 必须做
- `reports/` 加入 `.gitignore`
- SKILL.md 明确告诉 Claude："不要只看预设指标，要找未知模式；每个结论必须引用具体 case_id 证据"
- SKILL.md 必须含"工具自身改进建议"section 的撰写指引：要求 Claude 反思本次分析过程，列出脚本/SKILL 改进点
- 数据准备脚本必须能独立运行（不依赖 Claude Code），方便人工 debug
- 报告必须含元数据：分析时间窗、case 数量、生成时间戳、对应 git commit hash
- 每个 outlier case 在报告中给出指向具体 log 文件的相对路径（`logs/20260511-XXXXXX.json`）
- 脚本输出 markdown 必须遵循固定结构，方便 Claude 解析
- 报告生成后 Claude 主动询问用户是否实施工具改进，不能默默改
